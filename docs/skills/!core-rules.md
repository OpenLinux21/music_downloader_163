# !core-rules.md — 强制规则（任何任务前必读）

> 文件名以 `!` 开头：无论当前任务是什么，开展任何工作前必须完整读取并遵守本文件。
> 本文件与根目录 `AGENTS.md` 冲突时以 `AGENTS.md` 为准；发现冲突应报告用户而非自行裁决。

## 1. 语言规范

1. 所有新建及修改的 Markdown 文档、代码注释性质的说明、文档标题、章节、表格、列表、约束描述必须使用规范、准确、完整的简体中文。
2. 技术专有名词、代码符号、命令、路径、API 名称、标准字段及必要英文标识可保留原文。
3. 文件名可按工程惯例使用英文；正文不得整段使用英文或其他语言。

## 2. 事实性要求

1. 一切描述以代码实证为准，严禁根据文件名、注释、README 或猜测断言行为。
2. 无法确认的内容必须标记「待确认」并登记到 `docs/knowledge-base.md` 第 6 节，不得编造。
3. 文档引用代码位置使用「文件 + 类/函数名」，不引用行号。
4. 不得声称执行过实际未执行的测试或验证。

## 3. 凭据与仓库安全红线

1. **禁止**将以下内容加入任何 Git 提交：Cookie、密钥、凭据、`.env` 变量值、`music_api.log`、`downloads/` 产物、虚拟环境（`.venv/`）、`__pycache__/`。
2. `cookie.txt` 当前被 Git 跟踪（用户已确认为无用的示例凭据）。即使如此，每次提交前必须执行 `git status` 与 `git diff --cached` 检查暂存区，确认没有凭据、日志或产物混入。
3. 不修改 `.gitignore` 与 Git 跟踪状态，除非任务目标就是如此并经用户确认。
4. 不在文档中写入 Cookie 值、内网地址、真实账号信息。

## 4. 代码修改红线

1. 不得为生成文档、修文档或「顺手优化」而修改业务代码、改变程序行为、重构项目。
2. 不得安装非任务必需的依赖；`requirements.txt` 版本必须固定。
3. 修改代码时保持既有模式：响应统一走 `APIResponse`、上游调用一律经 `music_api` 封装、异常包装为 `APIException`/`DownloadException`。

## 5. Git 工作规则

1. 以 `develop` 为基准：任务开始时检查当前分支、`git status` 工作区状态与 `develop` 最新状态；在 `develop` 上创建任务分支后才开始修改。
2. 分支命名清晰表达目的：`docs/xxx`、`feat/xxx`、`fix/xxx`、`refactor/xxx`。
3. 修改必须形成合理 commit；提交信息简洁说明意图（中文或英文均可，保持仓库既有风格：`feat:`/`fix:`/`chore:`/`docs:` 前缀可用）。
4. 严禁：直接在 `develop` 上开发、未经用户明确同意合并任务分支、未经授权推送远程。
5. `develop` 不存在、工作区有无法安全处理的用户修改、或操作可能丢数据时：停止操作，向用户说明。

## 6. 验证要求（本项目无测试框架）

按改动范围选择，验证结果必须如实报告：

| 改动范围 | 标准验证方式 |
| --- | --- |
| 任何 Python 改动 | `.venv/bin/python -c "import main, music_api, music_downloader, qr_login"`（导入冒烟，确认无语法/导入错误） |
| 路由/接口改动 | 在上条基础上用 `main.app.test_client()` 对受影响路由做本地请求验证（无参数校验分支、错误分支必测） |
| 下载器改动 | 用 `python music_downloader.py <测试ID>` 验证信息获取；**下载与元数据写入需用户授权**（消耗上游与磁盘） |
| 纯文档改动 | 检查文档间引用路径有效、无内部矛盾；`git diff` 确认未触碰代码 |
| 部署配置改动 | 静态检查配置语法（如 `docker-compose config`）；构建类验证需用户授权 |

禁止在验证中发起真实上游解析/下载消耗（`/song`、`/download` 成功路径），除非用户明确要求。

## 7. 文档同步义务

1. 任务涉及代码变化时，按 `docs/doc-maintenance.md` 映射表在**同一次任务**中更新对应文档与知识库。
2. 知识库（`docs/knowledge-base.md`）是活文档：新事实、新问题、待确认事项随任务登记；已解决条目标注「已修复/已关闭」保留轨迹。
3. 重要设计决策写入 `docs/history.md`。
4. 新增文档登记到 `docs/doc-maintenance.md` 第 4 节；**不修改根目录 `AGENTS.md`**（永久固定文件，仅用户明确授权时可人工修改）。

## 8. 任务收尾报告模板

任务完成时必须向用户报告：修改内容摘要、涉及文件清单、验证方式与结果、commit ID、当前分支、遗留问题/待确认事项；并明确等待用户确认，不擅自合并。
